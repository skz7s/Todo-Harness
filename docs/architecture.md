# Architecture

DeepSeek Harness owns conversation history, session management, composer behavior, attachments, images, and voice input. Todo Harness extends the native Web profile with persistent Todo tools and a right-side work area for Todo, Schedule, statistics, Token usage, and settings.

```text
DeepSeek Harness Web UI
  ├── native conversation, session list, attachments, images, voice input
  ├── Todo tools ───────────┐
  ├── Todo work-area UI ────┴─ TodoRepository ── todos.json
  ├── Schedule UI/tools ────── Harness Schedule service
  ├── usage events ─────────── UsageRepository ── usage.json
  └── brand/budget settings ─ SettingsRepository ── settings.json
```

`src/plugins/dsh-todo-plugin.js` registers direct-persistence Todo tools and adds per-turn maintenance rules. Harness reads the latest list at the start of each turn and again before its final response, applies relevant changes directly, rereads after mutations, and describes confirmed changes.

`src/plugins/web-search.js` registers the `todo-harness-auto` search provider behind Harness's existing `web_search` tool. Each operation snapshots the initiating session's provider/model and the live provider settings, then sends an auxiliary native Responses, Anthropic, Gemini, or Perplexity search using that route's endpoint and credential. Official DeepSeek and protocols without a standard native search use the independent DeepSeek Search API. Provider/model overrides are live; native-search failures never silently route to a different vendor. Sources are mapped from structured search results or citation metadata, and ordinary model prose without search metadata is rejected. Responses uses the OpenAI SDK's SSE parser with explicit completion checks. Auxiliary model usage is appended as `web/model-search-usage` and persisted by the existing usage listener; DeepSeek Search has request billing rather than model token usage. The separate `web_fetch` provider remains local HTTP.

`src/dsh/client.js` contributes a right-side Todo container sized to one third of the viewport on desktop, with Today, Plan, and Scheduled segments. Today filters due and overdue tasks; Plan shows the full shared task set, including today's tasks. The matching Harness grid track keeps the conversation centered between the left session sidebar and Todo container. It hides the dock tab strip only while the Todo tab is selected, keeping the panel free of split controls; other tabs such as file previews retain their native tab and close controls. Folding Todo changes it into a 64px statistics rail with its own restore icon; the conversation track expands to fill the released width. On mobile, the left rail has a Todo toggle: the initial view is the conversation, and opening Todo fills the content area while hiding chat; toggling again returns to the conversation. The user can create, edit, complete, reopen, and delete Todo records through the loopback API. This UI and the Harness tools both use the same `TodoRepository`. Schedule entries are read and updated through the Harness Schedule Remote, using their original Session binding and full compare-and-update record; users can also create them from the panel. Todo and schedule action buttons send their work into a new Harness session.

The collapsed Todo rail shows Todo counts. Daily Token usage is displayed above Settings in the left sidebar, with a progress bar against the saved daily budget. Usage comes from Harness session events; the global daily budget is persisted as a Todo Harness preference and is shown as a usage threshold only. The agent name uses one persisted setting to drive the browser title, sidebar brand, and conversation brand mark. The native Models onboarding remains active for new profiles. DeepSeek is recommended, while the saved default provider/model can be changed; custom pi-ai reasoning levels are edited per model and then reflected in the model catalog.

`src/http/server.js` exposes Todo reads and mutations, usage, settings, and health to the exact loopback origin used by the Harness UI. Other origins are rejected. `TodoRepository`, `UsageRepository`, and `SettingsRepository` serialize writes to atomic JSON files. Harness browser authentication remains enabled; the launcher normally opens its local authenticated URL to exchange the per-process launch token for a signed cookie. DSH persists the signing secret in `$DSH_HOME/.credentials.yaml`, and its cookie lasts 30 days by default. The cookie is scoped to the exact hostname and port, so keep the same loopback address and port across browser visits; `--no-open` requires manually opening the printed URL for that running process. The launcher sets the DSH working directory to this project root and sets the DSH approval policy to `never` while keeping the workspace-write sandbox.

The launcher adds the voice-input Bundle to the Web profile automatically, so users do not need to visit the Plugins page. The local recognition model is downloaded on first use from the in-place voice setup dialog, which shows progress, cancellation, background download, and retry states. The profile patch keeps the standard preset, native attachment and voice input, the Schedule Host service and its agent tools. It does not register the separate Schedule management page; scheduled tasks are managed from the Todo segment. It disables mode selection, plugin management, approvals, feedback, activity/job controls, report cards, Session Log download, Session Log upload, and the specified settings sections. UI-only prompt and thinking copy are localized through a registered Harness locale, preserving the native conversation implementation.
